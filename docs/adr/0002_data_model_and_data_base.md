# ADR 0002: Модель данных и база данных

## Контекст

Входящие данные представляют собой файлы отчетов утилиты диагностики сетей (форматы `ibdiagnet`). Данные содержат
десятки метрик (секция `START_PORTS` содержит 54 колонки). Необходимо выбрать подход к хранению: гибридный (JSONB для
динамических атрибутов) или строгий реляционный (явные колонки для каждого поля).

## Решение

### 1. Строгая Реляционная Модель БД

Принято решение отказаться от `JSONB` и использовать строгую DDL-схему:

- Все атрибуты из примеров файлов явно прописываются как колонки в PostgreSQL.
- Это гарантирует максимальную целостность данных на уровне БД, строгую типизацию (через кодогенерацию `sqlc`) и
  избавляет от накладных расходов на парсинг JSON в рантайме.
- Значения вроде `N/A` или hex-строки (например, `0xffffffffff`) мапятся в тип `TEXT`, остальные метрики — в `INT` /
  `BIGINT`.

**Схема таблиц:**

- **`logs`**: Метаданные парсинга (статус обработки файла).
- **`nodes`**: Полный маппинг колонок секции `START_NODES` (`NodeDesc`, `NumPorts` и т.д.).
- **`ports`**: Полный маппинг 54 колонок секции `START_PORTS`.
- **`nodes_info`**: Агрегация `START_SYSTEM_GENERAL_INFORMATION` и `.sharp_an_info`.
- **`switches`**: Полный маппинг секций `START_SWITCH`, причем имеется связь с `node` в случае, когда тип будет
  `switch`.

### 2. Стратегия парсинга

* Используется паттерн `Scanner` (построчное чтение).
* Данные буферизуются и вставляются пакетно (Batch Insert) через функционал `COPY` (в `sqlc` это `:copyfrom`) для
  максимальной производительности записи.

### 3. Переход на ENUM для NodeType при парсинге

Был выбор либо оставить `NodeType` в качестве `INT` или переводить в человекочитаемый вариант с `ENUM`, был выбран
второй вариант для удобства конечного потребителя. 

### 4. Детерминированная генерация UUID для NodeID (v5) 

Для связи сущностей (например, привязки порта к узлу по `NodeGuid`) я отказался от хранения хэш-мап в памяти.
Вместо генерации случайных UUIDv4, `NodeID` вычисляется на лету (детерминированно) с использованием алгоритма `UUIDv5`
на основе `LogID` и строкового значения `NodeGuid`. Это позволяет парсеру связывать данные из разных файлов (основного
лога и конфигурации), работая в рамках строго ограниченного потребления памяти (O(1) по памяти для связей).

### 5. Прямой маппинг ENUM через sqlc Overrides

Вместо написания ручных конвертеров между сгенерированными типами `sqlc` и доменными моделями, используется директива
`overrides` в `sqlc.yaml`. Базовые типы `log_status` и `node_kind` напрямую транслируются кодогенератором в
`domain.LogStatus` и `domain.NodeKind`.

### 6. Трансляция ошибок (Error Translation) на границе слоев

Слой адаптера (`internal/adapters/postgres`) полностью инкапсулирует работу с `pgx`. Добавлена функция `translateError`,
которая перехватывает драйвер-специфичные ошибки (`pgx.ErrNoRows`) и специфичные коды PostgreSQL
(`23505` - нарушение уникальности, `23503` - конфликт внешних ключей), преобразуя их в доменные
ошибки (`domain.ErrNotFound`, `domain.ErrAlreadyExists`).
В логи добавляется контекст: имя метода репозитория и оригинальная ошибка драйвера.

### 7. Инкапсуляция пула соединений

Структура базы данных в слое адаптеров объявлена приватной (`type repository struct`). Экспортируется только
функция-конструктор `NewRepository`, возвращающая интерфейс `ports.Repository`. Это гарантирует, что пул `pgxpool`
недоступен извне, предотвращая выполнение несанкционированных "сырых" SQL-запросов из UseCase или хендлеров.

## Последствия

* **Позитивные**: 100% строгая типизация, предсказуемая схема, максимальная скорость выборки (SELECT) конкретных метрик
  для аналитики, явный контракт данных.
* **Негативные**: Широкие таблицы (Wide Tables), требующие аккуратности при написании SQL-запросов и DDL-миграций.
