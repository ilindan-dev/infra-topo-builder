# ADR 0004: Стратегия консистентности данных и загрузки связей (Lazy Loading)

## Статус

Принято (Accepted)

## Контекст

При разработке микросервиса `InfraTopoBuilder` возникли две взаимосвязанные проблемы, касающиеся обработки больших
объемов данных логов `ibdiagnet`:

1. **Управление транзакциями при пакетной вставке:** Парсинг гигабайтных файлов может занимать минуты. Оборачивание
   всего процесса в одну SQL-транзакцию (`BEGIN ... COMMIT`) приводит к раздуванию WAL (Write-Ahead Logging) в
   PostgreSQL, длительным блокировкам таблиц и высокому риску потери всего прогресса при малейшем обрыве сети.
2. **Структура ответа API (Топология графа):** Один коммутатор может содержать десятки портов, каждый из которых
   обладает обширным набором телеметрических метрик. Попытка вернуть всю древовидную структуру (Узлы -> Метаданные ->
   Сотни тысяч портов) в одном HTTP `GET` запросе (`Eager Loading`) приведет к исчерпанию оперативной памяти сервиса и
   таймаутам на клиенте из-за гигантского размера JSON-пейлоада.

## Решение

Принято решение внедрить стратегию Компенсации (Удаления) при ошибках и Ленивой загрузках (Lazy Loading) для портов .

### 1. Стратегия компенсации (Отказ от длинных транзакций)

* Батчи данных (`nodes`, `ports`, `node_info`) загружаются в БД в режиме автокоммита, без открытия глобальной
  транзакции.
* При возникновении критической ошибки парсинга, стейт-машина переводит сущность `Log` в статус `error`.
* Бизнес-логика или фоновый воркер вызывает метод `DeleteLog`. Благодаря внешним ключам `ON DELETE CASCADE` в схеме БД,
  все миллионы "грязных" строк, связанных с этим `log_id`, удаляются атомарно и мгновенно.
* *Обоснование:* Это гарантирует высокую скорость `COPY/UPSERT` и защищает БД от блокировок.

### 2. Ленивая загрузка (Lazy Loading)

* Эндпоинт `/api/v1/topology/{log_id}` возвращает **Дерево инвентаризации (Inventory Tree)**: список узлов (коммутаторы
  и хосты) и их агрегированные метаданные (из `.sharp_an_info`), **без вложения массива портов**.
* Массив портов для конкретного узла запрашивается клиентом (фронтендом) отдельным асинхронным запросом к эндпоинту
  `/api/v1/port/{node_id}` только по мере необходимости (например, при клике/раскрытии узла в UI).
* *Обоснование:* Поддерживает контракты API легковесными, предотвращает проблему OOM (Out Of Memory) на сервере и
  клиенте, соответствует изначальному дизайну REST API (наличие отдельного эндпоинта для портов).

## Последствия

* **Позитивные:**
    * Экстремально высокая пропускная способность при парсинге.
    * Быстрый и предсказуемый ответ эндпоинта `/topology` (O(1) по памяти относительно портов).
    * Идеальное соответствие принципам REST (сущности разнесены по разным ресурсам).
* **Негативные:**
    * Фронтенду потребуется делать N+1 запросов, если пользователь захочет "Раскрыть все узлы" одновременно (решается
      пагинацией на клиенте).
    * В случае аппаратного сбоя (Hard Crash) микросервиса до вызова `DeleteLog`, в БД могут остаться "осиротевшие"
      записи со статусом лога `in_progress`.
