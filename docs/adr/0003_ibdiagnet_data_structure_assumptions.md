# ADR 0003: Допущения о структуре входных данных и стратегия FSM-парсера

## Статус

Принято (Accepted)

## Контекст

На вход микросервису поступает архив с результатами работы утилиты диагностики сети `ibdiagnet` (обычно директория `ibdiagnet2/`). Внутри архива содержится множество файлов (логи, таблицы маршрутизации, LST-файлы и т.д.).
Для проектирования высокопроизводительного парсера с минимальным потреблением оперативной памяти (O(1)) необходимо четко определить границы и структуру целевых данных. Обработка сценариев с фрагментированными или дублирующимися файлами потребовала бы загрузки промежуточных состояний в RAM или сложных механизмов слияния (MapReduce) на стороне БД.

## Решение

Принято решение зафиксировать жесткий контракт ожидаемых данных, основанный на текущем поведении утилиты `ibdiagnet`:

1. **Единственность целевых файлов в архиве:**
   Парсер исходит из допущения, что в загруженном архиве находится строго **один** релевантный файл с расширением `.db_csv` (содержащий топологию) и строго **один** файл `.sharp_an_info` (содержащий расширенную информацию об узлах). Все остальные файлы в архиве игнорируются сканером.

2. **Линейность и уникальность информационных блоков:**
   Допускается, что внутри файла `.db_csv` ключевые секции (например, `START_NODES ... END_NODES`, `START_PORTS ... END_PORTS`, `START_SWITCHES ... END_SWITCHES`) встречаются **строго один раз**.

3. **Следствие: Потоковый конечный автомат (FSM):**
   Опираясь на пункты 1 и 2, парсер реализуется на базе паттерна "Конечный автомат" (Finite State Machine).
   - Файл читается построчно (через `bufio.Scanner`).
   - Триггеры вида `START_<SECTION>` переключают состояние автомата.
   - Данные внутри секции накапливаются в буфер (размером `BATCH_SIZE` из конфигурации).
   - При достижении лимита буфера или встрече триггера `END_<SECTION>` происходит сброс (flush) батча напрямую в базу данных через механизм `PostgreSQL COPY`.
   - Состояние сбрасывается, автомат ожидает следующий блок.

## Последствия

- **Позитивные:** 
  - **Экстремально низкое потребление памяти.** Независимо от того, весит ли лог 10 МБ или 10 ГБ, сервис потребляет фиксированный объем RAM (равный размеру одного батча).
  - **Скорость разработки и надежность.** Логика парсера становится плоской и предсказуемой, исключаются гонки данных (data races) при сборке графа топологии в памяти.
- **Негативные:**
  - **Хрупкость контракта.** Если в будущих мажорных версиях `ibdiagnet` изменит формат вывода (например, начнет разбивать `db_csv` на чанки по 1000 узлов или повторять секции), микросервис отвергнет файл или запишет данные некорректно.
  - **Митигация рисков:**
    В логику парсера должен быть встроен валидатор. Если FSM встречает секцию `START_SWITCHES` во второй раз за одну сессию парсинга, он должен немедленно прервать работу, откатить транзакцию (или изменить статус `log` на `error` для каскадного удаления) и вернуть соответствующую ошибку контракта.
